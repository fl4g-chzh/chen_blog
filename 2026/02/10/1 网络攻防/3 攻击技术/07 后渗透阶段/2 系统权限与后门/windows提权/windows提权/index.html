态势感知

在任何情况下，无论是日常生活还是进行网络渗透测试等项目，确定自身所处的时空位置始终都很重要。如果没有对当前周围环境的了解，我们就无法有效运作和反应。我们需要这些信息来做出关于下一步行动的明智决策，从而能够主动而不是被动地操作。当我们登陆 Windows 或 Linux 系统，打算下一步提升权限时，有几点是我们应该始终寻找的，以便规划接下来的行动。我们可能会发现可以直接访问的其他主机，需要绕过的保护措施，或者发现某些工具无法在目标系统上使用。

保护机制

大多数现代环境都运行着某种反病毒或端点检测与响应（EDR）服务，用于主动监控、警报和阻止威胁。这些工具可能会干扰枚举过程。在特权提升过程中，它们很可能会构成某种挑战，特别是如果我们使用的是某种公共 PoC 漏洞利用工具。枚举现有的保护机制将有助于我们确保所使用的方法没有被阻止或检测到，并且在我们需要在使用前定制有效载荷或修改工具时，将有助于我们。

许多组织使用某种应用程序白名单解决方案来控制特定用户可以运行的应用程序和文件类型。这可用于尝试阻止非管理员用户运行 cmd.exe 或 powershell.exe 或其他日常工作中不需要的二进制文件和文件类型。微软提供的一个流行解决方案是 AppLocker。我们可以使用 GetAppLockerPolicy cmdlet 来枚举本地、有效（强制执行）和域 AppLocker 策略。这将帮助我们查看可能被阻止的二进制文件或文件类型，以及我们是否需要在枚举期间或运行工具或技术以提升权限之前执行某种 AppLocker 绕过。

windows安全性

Windows 安全性主要依赖于四个基本元素之间的交互：访问令牌 (Access Token)、安全标识符 (SID)、安全描述符 (Security Descriptor)、访问检查 (Access Check)。

访问令牌 (Access Token)：用户的“身份证”

访问令牌是用户登录时系统创建的，伴随用户的所有进程。它本质上定义了两个关键概念：Permission (权限) 和 Privilege (特权)。

权限 vs 特权 (关键区别)

虽然两者听起来相似，但在 Windows 内核中机制完全不同：

  • Permission (权限/访问权): 是针对对象的。
    • 例如：是否有权“读取”某个文件、是否有权“写入”注册表。它是通过对比令牌与对象的 ACL 来决定的。
  • Privilege (特权): 是针对系统的。
    • 例如：是否有权“更改系统时间” (SeSystemtimePrivilege)、“关闭系统” (SeShutdownPrivilege) 或“调试程序” (SeDebugPrivilege)。特权直接存储在访问令牌中，使用前通常需要代码显式开启（Enable）。

      令牌的组成

      访问令牌包含了关于安全上下文的所有信息：
  • 用户 SID: 用户的唯一标识。
  • 组 SID: 用户所属组（如 Administrators）的列表。
  • 特权列表 (Privileges): 用户拥有的系统能力。
  • 登录 SID: 标识当前的登录会话。
  • 默认所有者/默认组/默认 DACL: 当该用户创建新对象时，默认赋予该对象的安全属性。
  • 令牌类型: 主令牌 (Primary) 或 模拟令牌 (Impersonation)。

安全标识符 (SID)：身份的“编码”

SID 是二进制格式的数据结构，是 Windows 系统中用于唯一识别用户、组或计算机的“身份证号”。

SID 结构

结构中的第一个值包含 SID 结构的相关信息，其余值按层级排列。

格式示例: S-1-5-32-544

  • S: 代表这是一个 SID 标识。
  • 1: 修订版本号 (Revision Level)。
  • 5: 标识符授权机构 (Identifier Authority)，5 代表 NT Authority。
  • 32: 子授权机构/域标识符 (Sub-authority)，32 代表 Builtin (内置域)。
  • 544: 相对标识符 (RID)，544 代表 Administrators (管理员组)。

已知 SID (Well-known SIDs)

这是系统预留的、具有固定含义的 SID，分为几类：

  • RID 500-999: 保留给内置账户和组。
    • S-1-5-32-544: Administrators (管理员组)。
    • S-1-5-32-545: Users (普通用户组)。
    • SID ending in 500: 默认的 Administrator 账户。
    • SID ending in 501: Guest 账户。
  • 服务隔离相关的已知 SID (Windows 2003+ 引入):
    • S-1-5-18 (LocalSystem): 拥有本地最高权限。在网络访问时，它代表计算机本身 (DOMAIN\Computer$)。
    • S-1-5-19 (LocalService): 权限受限的服务账户。访问网络时相当于匿名用户 (Anonymous)。
    • S-1-5-20 (NetworkService): 权限受限的服务账户。但访问网络时使用计算机账户 (身份同 LocalSystem)。

安全描述符 (Security Descriptor)：对象的“锁”

每个安全对象（文件、注册表、进程等）都有一个安全描述符。它是连接“用户”和“资源”的桥梁。

安全描述符包含四个主要部分：

  1. Owner SID (所有者): 拥有该对象的用户。所有者永远有权修改 DACL（即可以把权限赋予自己），即使他当前被拒绝访问。
  2. Group SID (组): 主要用于 POSIX 兼容，现代 Windows 较少使用。
  3. DACL (自主访问控制列表): 最核心部分。
    • 决定了“谁”可以对这个对象“做什么”。
    • 包含一系列 ACE (Access Control Entries)。
    • 如果没有 DACL (Null DACL)，则允许所有人完全控制；如果是空的 DACL (Empty DACL)，则拒绝所有人访问。
  4. SACL (系统访问控制列表):
    • 用于审计 (Auditing)。
    • 记录谁成功或失败地访问了对象（例如：记录谁试图删除这个文件）。

访问检查机制 (Access Check)：开锁的过程

当一个用户进程试图访问一个对象时，内核中的 SRM (Security Reference Monitor，安全引用监视器) 会执行访问检查算法。

SRM 会将 访问令牌中的 SID 与 对象 DACL 中的 ACE 进行逐条匹配。

匹配规则 (Canonical Order)

DACL 中的 ACE 通常按照 Deny (拒绝) 在前，Allow (允许) 在后 的规范顺序排列。

检查流程

SRM 按照顺序从上到下扫描 DACL：

  1. 显式拒绝 (Explicit Deny):
    • 如果遇到一条 Deny 条目且 SID 匹配（如“拒绝 User A 读取”），SRM 立即停止扫描并拒绝访问。
    • 结论：Deny 权限具有最高优先级。
  2. 累积允许 (Cumulative Allow):
    • 如果遇到 Allow 条目且 SID 匹配，SRM 会累积授予该条目中的权限。
    • 扫描继续，直到用户请求的所有权限都被满足。
    • 一旦所有请求的权限都集齐，SRM 停止扫描并允许访问。
  3. 隐式拒绝 (Implicit Deny):
    • 如果扫描完整个 DACL，用户请求的权限仍未全部被满足（或者 DACL 为空），则拒绝访问。
    • _结论：默认情况下，未明确允许即为拒绝。_

土豆攻击

合法程序可能会利用另一个进程的令牌从管理员提升到本地系统，后者具有额外的权限。进程通常通过调用 WinLogon 进程来获取 SYSTEM 令牌，然后使用该令牌执行自身，将其置于 SYSTEM 空间中。攻击者经常滥用这种权限，在“土豆风格”的权限提升中——其中服务账户可以 SeImpersonate ，但不能获得完整的 SYSTEM 级别权限。本质上，土豆攻击欺骗了以 SYSTEM 身份运行的进程连接到它们的进程，后者交出令牌供其使用。

SeDebugPrivilege

要运行特定的应用程序或服务或协助故障排除，用户可能会被分配 SeDebugPrivilege 而不是将账户添加到管理员组中。此权限可以通过本地或域组策略在 Computer Settings > Windows Settings > Security Settings 下分配。默认情况下，只有管理员被授予此权限，因为它可用于从系统内存捕获敏感信息，或访问/修改内核和应用程序结构。此权限可能会分配给需要作为日常工作的一部分调试新系统组件的开发人员。此用户权限应该谨慎分配，因为任何被分配此权限的账户都将能够访问关键操作系统组件。

我们可以使用 SysInternals 套件中的 ProcDump 来利用这个权限并转储进程内存。一个攻击方向是本地安全授权子系统服务 (LSASS) 进程，该进程在用户登录系统后会存储用户凭证。

我们可以使用 sekurlsa::minidump 命令在 Mimikatz 中加载这个。在执行 sekurlsa::logonPasswords 命令后，我们获得了本地管理员账户的 NTLM 哈希值（本地登录）。我们可以使用这个来执行密码传递攻击以横向移动，如果一台或多台其他系统（在大组织中很常见）上使用了相同的本地管理员密码。

远程代码执行为 SYSTEM

我们也可以利用 SeDebugPrivilege 进行 RCE。使用这种技术，我们可以通过启动子进程并利用 SeDebugPrivilege 授予我们账户的提权权限来将权限提升至 SYSTEM。通过这种方式，我们可以修改正常系统行为，继承父进程的令牌并模拟它。如果我们目标是运行为 SYSTEM 的父进程（指定目标进程的进程 ID（或 PID）或正在运行的可执行程序），那么我们可以快速提升权限。

SeTakeOwnershipPrivilege

SeTakeOwnershipPrivilege 授予用户获取任何“可安全对象”的所有权的能力，这意味着 Active Directory 对象、NTFS 文件/文件夹、打印机、注册表键、服务和进程。此权限授予对象上的 WRITE_OWNER 权限，这意味着用户可以在对象的安全描述符中更改所有者。管理员默认被分配此权限。

虽然遇到具有此权限的标准用户账户的情况很少，但我们可能会遇到一个服务账户，例如，被分配此权限以运行备份作业和 VSS 快照。它也可能被分配其他几个，例如 SeBackupPrivilege 、 SeRestorePrivilege 和 SeSecurityPrivilege ，以更细粒度地控制此账户的权限，并且不授予账户完全的本地管理员权限。这些权限本身可能被用来提升权限。然而，有时我们可能需要获取特定文件的所有权，因为其他方法 ds 被阻止，或者以其他方式无法按预期工作。滥用这种权限有点是边缘情况。不过，深入了解它是有价值的，特别是因为我们可能也会在 Active Directory 环境中发现自己处于可以分配这项权限给特定用户、我们可以控制并利用它来读取文件共享上的敏感文件的情况。

拥有这种权限，用户可以拥有任何文件或对象，并做出可能涉及敏感数据、 Remote Code Execution （ RCE ）或 Denial-of-Service （DOS）的更改。

DnsAdmins

DnsAdmins 组的成员可以访问网络上的 DNS 信息。Windows DNS 服务支持自定义插件，并可以从它们调用函数来解析不在任何本地托管 DNS 区域范围内的名称查询。DNS 服务以 NT AUTHORITY\SYSTEM 身份运行，因此在这个组中的成员可能会被利用来提升域控制器或在一个单独的服务器充当域 DNS 服务器的情况下的权限。

可以使用内置的 dnscmd 工具来指定插件 DLL 的路径,可以执行以下攻击：

  • DNS 管理通过 RPC 进行
  • ServerLevelPluginDll 允许我们加载自定义 DLL，而无需验证 DLL 的路径。这可以通过命令行使用 dnscmd 工具完成
  • 当 DnsAdmins 组的成员运行下面的 dnscmd 命令时， HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\services\DNS\Parameters\ServerLevelPluginDll 注册表键将被填充
  • 当 DNS 服务重新启动时，将加载此路径下的 DLL（即域控制器机器账户可以访问的网络共享）
  • 攻击者可以加载自定义 DLL 以获取反向 shell，甚至可以将 Mimikatz 之类的工具作为 DLL 加载以转储凭证。

加载自定义 DLL

只有 dnscmd 工具可以被 DnsAdmins 组的成员使用，因为他们没有直接对注册表键的权限。

在配置了包含我们恶意插件的路径的注册表设置，并且我们的有效负载创建完成后，DLL 将在 DNS 服务下次启动时被加载。属于 DnsAdmins 组的成员并没有重启 DNS 服务的权限，但这在理论上系统管理员可能会允许 DNS 管理员这样做。

在重启 DNS 服务后（如果我们的用户有此权限级别），我们应该能够运行我们的自定义 DLL 并添加用户（在我们的例子中）或获取反向 shell。如果我们没有重启 DNS 服务器的权限，我们将不得不等待服务器或服务重启。让我们检查我们当前用户在 DNS 服务上的权限。

Hyper-V管理员

Hyper-V 管理员组拥有对所有 Hyper-V 功能的完全访问权限。如果域控制器已被虚拟化，那么虚拟化管理员应被视为域管理员。他们可以轻松地创建活动域控制器的克隆，并在离线状态下挂载虚拟磁盘以获取 NTDS.dit 文件，并提取域中所有用户的 NTLM 密码哈希。

删除虚拟机时， vmms.exe 会尝试恢复对应 .vhdx 文件的原始文件权限，并且以 NT AUTHORITY\SYSTEM 的身份执行，不会模拟用户身份。我们可以删除 .vhdx 文件，并创建一个本地硬链接指向受保护的 SYSTEM 文件，从而获得完全的权限。

如果操作系统易受 CVE-2018-0952 或 CVE-2019-0841 漏洞影响，我们可以利用这一点来获取 SYSTEM 权限。否则，我们可以尝试利用服务器上安装了在 SYSTEM 上下文中运行的服务的应用程序，该服务可被非特权用户启动。
